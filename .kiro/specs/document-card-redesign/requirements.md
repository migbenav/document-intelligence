# Requirements Document

Document Card Redesign (Rediseño de la Card de Documento)

## Introduction

This feature redesigns the Document Card to present coherent, useful information in under 2 minutes, separating the technical sheet (local, instantaneous) from the content analysis (LLM). It incorporates a formal 4-level document classification system based on ISO/archival document typologies, and reduces LLM dependency by leveraging Python libraries for local analysis (lingua-py for language detection, textstat for readability metrics).

The redesign evolves the original base-analysis card into a two-section layout: a "Ficha Técnica" (Technical Sheet) that appears instantly with no LLM dependency, and a "Contenido" (Content) section that populates when the LLM responds. The classification system replaces the flat single-value classification with a 4-level taxonomy (Scope → Purpose → Genre → Format) plus a free-text descriptor and confidence score.

This spec replaces and evolves the `base-analysis` spec regarding card display and classification. The `base-analysis` spec remains as historical reference of the original implementation.

## Feature Boundaries

**In scope:**
- New local analysis using lingua-py (language detection) and textstat (readability index).
- TextStatsAnalyzer module: word count, sentence count, paragraph count, readability score — all local, no LLM.
- 4-level document classification taxonomy with bilingual labels (ES display, EN code).
- New LLM prompt v3 that receives local hints and only asks for: summary, 4-level classification, topics, audience.
- LocalAnalyzer v2 that generates classification hints from title patterns and document organization.
- Frontend: single card with two sections (Ficha Técnica + Contenido), collapsible "Más detalles", tooltips.
- Confidence score for classification (LLM self-assessed + local/LLM agreement factor).
- Document lifecycle indicator: "vivo" (living) vs "congelado" (frozen) based on classification.
- Corporate document detection (is_corporate flag) with informational banner for non-corporate.
- Removal of redundant ProcessingStatus card (filename/language/chunks shown at step=ready).
- Backward compatibility: existing cards without new fields continue to render correctly.

**Out of scope:**
- Database migration (JSONB absorbs new fields without schema changes).
- On-demand analyses (C3) — separate spec.
- Multi-document classification or cross-document analysis.
- Custom user-defined taxonomies.
- Classification model training or fine-tuning.
- Block-level analysis (C4).

## Glossary

| Term | Definition |
|------|------------|
| Ficha_Técnica | The instantaneous section of the Document Card produced entirely by local processing (no LLM): format, size, language, word count, readability, organization, sections, levels. |
| Contenido | The LLM-generated section of the Document Card: executive summary, topic tags, 4-level classification chain, audience, purpose. |
| Classification_Chain | The 4-level taxonomy displayed as "Scope → Purpose → Genre → Format (confidence%)" — e.g., "Institucional → Normativo → Prescriptivo → Reglamento (87%)". |
| Confidence_Score | A percentage (0-100) indicating how confident the system is in the classification. Derived from LLM self-assessment adjusted by local/LLM hint agreement. |
| Living_Document | A document whose classification (normative/operational genre + prescriptive/instructive/bilateral genre) suggests it is actively maintained and may change over time. Activates all analyses. |
| Frozen_Document | A document classified as informational + expository, suggesting it captures a point-in-time state. Has limited analysis options. |
| LocalAnalyzer_v2 | Enhanced version of LocalAnalyzer that adds lingua-py language detection, textstat metrics, and classification hint generation via pattern matching. |
| LLMAnalyzer_v3 | Updated LLM analyzer with prompt v3 that does NOT ask for language/stats (handled locally), and adds 4-level classification, topics, and audience. |
| Prompt_v3 | The new prompt template (version "card-redesign-v3") that receives local hints and requests structured classification output. |
| Hint | A suggested classification value generated by local pattern matching (title keywords, organization type) passed to the LLM as context to improve accuracy. |
| lingua-py | Python library (lingua-language-detector>=2.0.0) for accurate language detection, replacing the manual stopword-based detector. |
| textstat | Python library (textstat>=0.7.0) for computing readability indices and text statistics (sentences, syllables, readability scores). |
| is_corporate | Boolean flag indicating whether a document appears to be a corporate/institutional document. Non-corporate documents show an informational banner. |

## Requirements

### Requirement 1: Local Text Statistics (TextStatsAnalyzer)

**User Story:** As a user, I want to see word count, sentence count, paragraph count, and readability score instantly after upload so that I can gauge the document's complexity without waiting for AI analysis.

#### Acceptance Criteria

1. WHEN a document completes ingestion, THE system SHALL compute text statistics locally using textstat and native Python: total word count, total sentence count, total paragraph count, and a readability index (Fernández-Huerta for Spanish, Flesch Reading Ease for English, raw score for other languages).
2. WHEN computing text statistics, THE system SHALL operate exclusively on the IR text content without any network or LLM calls.
3. THE text statistics computation SHALL complete in under 200 milliseconds for documents up to 10 MB.
4. WHEN the detected language is Spanish, THE readability index SHALL use the Fernández-Huerta formula via textstat. WHEN the detected language is English, THE readability index SHALL use Flesch Reading Ease. For other languages, THE system SHALL compute a raw Flesch score and label it as approximate.
5. THE readability score SHALL be presented with a human-readable label using strict boundary validation: "Muy fácil" (score > 80), "Fácil" (score > 60 AND score ≤ 80), "Normal" (score > 40 AND score ≤ 60), "Difícil" (score > 20 AND score ≤ 40), "Muy difícil" (score ≤ 20). THE system SHALL enforce boundary checking to prevent scores from mapping to incorrect labels.

**Traceability:**
- Card layout "Ficha Técnica" section: palabras, oraciones, párrafos, legibilidad.
- Dependency: textstat>=0.7.0.
- Cambio clave #2: TextStatsAnalyzer.

### Requirement 2: Language Detection with lingua-py

**User Story:** As a user, I want reliable language detection that never shows "Unknown" so that the document card always displays a meaningful language indicator.

#### Acceptance Criteria

1. WHEN the local analysis phase runs, THE system SHALL detect the document language using lingua-py (lingua-language-detector) instead of the manual stopword-based approach.
2. THE language detection SHALL support at minimum: Spanish (es), English (en), Portuguese (pt), French (fr), German (de), Italian (it). For languages not in this set, THE system SHALL display the ISO 639-1 code detected by lingua-py.
3. THE system SHALL NEVER display "Unknown" as a language. If lingua-py cannot determine the language with a confidence above 30%, THE system SHALL display "Indeterminado" with the top candidate and its confidence percentage. The 30% threshold ensures "Indeterminado" appears only when detection completely fails.
4. THE language detection SHALL operate on the first 5000 characters of the document text and complete in under 100 milliseconds. IF detection times out, THE system SHALL retry with progressively smaller text samples (2500, 1000 characters) until it completes within the time limit.
5. THE detected language SHALL be stored in the card's file_metadata and used to select the appropriate readability formula in Requirement 1.

**Traceability:**
- Cambio clave #1: Reemplazar LanguageDetector manual con lingua-py.
- Dependency: lingua-language-detector>=2.0.0.

### Requirement 3: 4-Level Document Classification Taxonomy

**User Story:** As a user, I want to see a formal multi-level classification of my document so that I understand its scope, purpose, genre, and specific format at a glance.

#### Acceptance Criteria

1. WHEN the LLM analysis completes, THE system SHALL produce a 4-level classification with:
   - Level 1 (Scope/Ámbito): one of `institutional`, `governmental`, `private`, `other`
   - Level 2 (Purpose/Propósito): one of `normative`, `operational`, `informational`, `evidentiary`, `contractual`
   - Level 3 (Genre/Género): one of `prescriptive`, `instructive`, `expository`, `registral`, `bilateral`
   - Level 4 (Format/Formato): one of `regulation`, `policy`, `manual`, `procedure`, `protocol`, `guide`, `minutes`, `contract`, `other`
   - Plus a free-text descriptor (Level 5): e.g., "Reglamento Interno", "Protocolo de Incendios"

2. WHEN the classification is displayed, THE system SHALL show the chain in Spanish using bilingual mapping: "Institucional → Normativo → Prescriptivo → Reglamento (87%)" where the percentage is the confidence score.

3. EACH classification level SHALL have a confidence score (0-100). The displayed confidence SHALL be the minimum across all 4 levels (weakest link).

4. IF the LocalAnalyzer provides classification hints (from title patterns and organization type), AND the LLM classification agrees with the hints, THEN THE confidence score SHALL be boosted by up to 10 points (capped at 99). IF they disagree, THE confidence SHALL be reduced by 10 points (minimum 10).

5. THE classification result SHALL be persisted as a structured object (`DocumentClassificationResult`) containing all 4 levels, the descriptor, individual level confidences, and the aggregated confidence.

6. THE system SHALL validate that the LLM response contains valid enum values for each level. IF any level has an invalid value, THE system SHALL default that level to "other"/"otro" with confidence 0.

**Traceability:**
- Taxonomía de clasificación (4 niveles + descriptor) specification.
- Cambio clave #3: Nueva taxonomía DocumentClassificationResult.
- Correspondencia bilingüe defined in context.

### Requirement 4: LLM Prompt v3 (Reduced Scope)

**User Story:** As a developer, I want the LLM prompt to focus only on semantic analysis (summary, classification, topics, audience) so that local processing handles everything it can deterministically.

#### Acceptance Criteria

1. WHEN the LLM analysis phase executes, THE system SHALL use prompt version "card-redesign-v3" which requests ONLY: executive summary (2-3 lines), 4-level classification (with confidence per level), topic keywords (3-5), target audience, and document lifecycle indicator (living/frozen).
2. THE prompt SHALL NOT ask the LLM for: language detection, word count, sentence count, paragraph count, readability score, or any statistics that the local analyzer provides.
3. THE prompt SHALL include "hints" from the local analyzer: suggested classification levels derived from title keywords and organization type patterns, detected language, and document size category (short <5 pages, medium 5-20, long >20).
4. THE prompt SHALL instruct the LLM to respond with a single JSON object. THE system SHALL distinguish between malformed JSON (non-parseable response — treated as LLM failure, creates partial card) and valid JSON with unexpected schema (wrong field names or types — logged as system error, also creates partial card but with different error classification for debugging).
5. THE LLM call SHALL have a timeout of 10 seconds. On any LLM failure (timeout, malformed response, parsing error, service error), THE system SHALL persist a partial card with Ficha Técnica data and no Contenido section, provided local analysis completed successfully.
6. THE system SHALL send only document text (first 10 chunks, max 2000 chars), local hints, and the system prompt. No user identity, document_id, session history, or account metadata SHALL be included.

**Traceability:**
- Cambio clave #4: Nuevo prompt v3.
- Cambio clave #5: LocalAnalyzer genera hints.
- Pipeline step 3: LLMAnalyzer v3 recibe hints del local.
- Restricción: Una sola llamada LLM con timeout 10s.

### Requirement 5: Card Layout — Two Sections with Collapsibles

**User Story:** As a user, I want a single document card with clear separation between instant technical data and AI-generated content so that I know what's immediately available and what requires processing.

#### Acceptance Criteria

1. WHEN a document card is displayed, THE UI SHALL render a single card with two visually distinct sections: "Ficha Técnica" (top) and "Contenido" (bottom).

2. THE "Ficha Técnica" section SHALL display immediately (no loading state) with visible fields: file format, file size (human-readable), detected language, and word count. Below these, a collapsible "Más detalles" section SHALL contain: sentence count, paragraph count, readability index with label, organization type, sections detected, hierarchy levels, and upload date. Each field SHALL have a tooltip icon with a brief description.

3. THE "Contenido" section SHALL display a loading skeleton while the LLM is processing. WHEN the LLM responds, IT SHALL show: executive summary (2-3 lines), topic tags (3-5 keywords as badges), and the classification chain with confidence percentage. Below these, a collapsible "Más detalles" section SHALL contain: document purpose, target audience, content-mix note (if applicable), and living/frozen indicator.

4. WHEN the card has status "partial" (LLM failed), THE "Contenido" section SHALL display a retry button ("Reintentar análisis") instead of placeholder or empty content.

5. WHEN a document is classified as non-corporate (is_corporate=false), THE card SHALL display an informational banner: "Este documento no parece ser un documento corporativo. El análisis puede ser menos preciso."

6. THE card component SHALL use shadcn/ui components (Card, Badge, Button, Skeleton, Tooltip, Collapsible) and follow existing frontend patterns (Tailwind CSS, React + TypeScript).

7. THE card component SHALL be accessible: all interactive elements keyboard-navigable, collapsible sections announced via ARIA attributes (aria-expanded, aria-controls), loading states via ARIA live regions, badge text with WCAG 2.1 AA contrast (4.5:1 minimum).

8. THE card SHALL be backward compatible: if a card object lacks new fields (text_stats, classification chain), the UI SHALL gracefully hide those sections rather than crash or show errors.

**Traceability:**
- Card layout specification from context.
- Cambio clave #6: Una card con secciones Ficha Técnica + Contenido.
- Cambio clave #7: Eliminar ProcessingStatus redundante.
- Restricción: Backward compatible.

### Requirement 6: Local Classification Hints

**User Story:** As a system, I want to generate classification hints from local patterns so that the LLM has contextual guidance and classification accuracy improves.

#### Acceptance Criteria

1. WHEN the LocalAnalyzer v2 processes a document, IT SHALL generate classification hints by analyzing: the document title (keyword matching against known patterns), the detected organization type, and structural patterns (e.g., numbered articles suggest normative+prescriptive+regulation).

2. THE hint generation SHALL use a configurable mapping of patterns to classification suggestions:
   - Title contains "reglamento|regulación|norma" → scope:institutional, purpose:normative, genre:prescriptive, format:regulation
   - Title contains "manual" → purpose:operational, genre:instructive, format:manual
   - Title contains "procedimiento|proceso" → purpose:operational, genre:instructive, format:procedure
   - Title contains "protocolo" → purpose:operational, genre:instructive, format:protocol
   - Title contains "guía|guia" → purpose:operational, genre:instructive, format:guide
   - Title contains "acta" → purpose:evidentiary, genre:registral, format:minutes
   - Title contains "contrato|convenio|acuerdo" → purpose:contractual, genre:bilateral, format:contract
   - Title contains "política|politica|policy" → purpose:normative, genre:prescriptive, format:policy
   - Organization type "numbered_articles" → genre:prescriptive

3. THE hints SHALL be passed to the LLM as a "suggested_classification" field in the prompt context. THE LLM is free to override hints — they are suggestions, not constraints.

4. IF no patterns match, THE system SHALL pass empty hints (no suggestion) and the LLM classifies from scratch.

5. THE hint generation SHALL also determine `is_corporate`: a document is considered corporate if its hints suggest any scope other than "private" OR if organizational patterns (articles, sections, numbered clauses) are detected. Default is `is_corporate=true` — only explicitly personal/private documents are flagged as non-corporate.

**Traceability:**
- Cambio clave #5: LocalAnalyzer genera hints de clasificación por patrones.
- Pipeline step 2: LocalAnalyzer v2 pattern matching.
- Restricción: Si local y LLM no coinciden → confidence baja.

### Requirement 7: Document Lifecycle (Living vs Frozen)

**User Story:** As a user, I want to know if a document is "living" (actively maintained) or "frozen" (point-in-time snapshot) so that I understand whether its content may change over time.

#### Acceptance Criteria

1. WHEN the classification is determined, THE system SHALL categorize the document lifecycle as:
   - "living" (vivo): documents with format in [regulation, policy, manual, procedure, protocol, guide, minutes, contract] — these are actively maintained documents.
   - "frozen" (congelado): documents with purpose=informational AND genre=expository — these capture a point-in-time state.

2. WHEN a document is "living", THE system SHALL enable all available on-demand analyses.

3. WHEN a document is "frozen", THE system SHALL indicate limited analysis availability in the card's "Más detalles" section with text: "Documento congelado — análisis limitados disponibles."

4. THE lifecycle indicator SHALL be displayed in the "Contenido > Más detalles" section as a badge: green "Documento vivo" or blue "Documento congelado".

5. IF the LLM completely failed (no classification data returned), THE lifecycle SHALL default to "living" (assume all analyses are available). IF a partial classification was obtained that explicitly indicates "frozen" (purpose=informational AND genre=expository), THE system SHALL honor the partial result and set lifecycle to "frozen".

**Traceability:**
- Cambio clave #8: Documentos "vivos" activan todos los análisis. Documentos "congelados" tienen análisis limitados.

---

### Requirement 8: ProcessingStatus Simplification

**User Story:** As a user, I don't want to see a redundant processing status card (filename, language, chunks) when the document card already shows all that information more completely.

#### Acceptance Criteria

1. WHEN a document card (even partial) is available, THE system SHALL NOT display the legacy ProcessingStatus component that previously showed filename, language, and chunk count during the "ready" step.
2. THE ProcessingStatus component SHALL only be shown during active ingestion (before status=ready) to indicate upload progress.
3. WHEN transitioning from ingestion to card display, THE UI SHALL seamlessly replace the ProcessingStatus with the DocumentCardView (Ficha Técnica section appears immediately, Contenido section shows skeleton).
4. THE ProcessingStatus component code SHALL be simplified to remove fields now handled by the card (language, chunks info) and retain only: upload progress bar, filename, and processing step indicator.

**Traceability:**
- Cambio clave #7: Eliminar ProcessingStatus redundante.
- Card layout: Ficha Técnica replaces the info previously in ProcessingStatus.

---

### Requirement 9: Backward Compatibility and Persistence

**User Story:** As a system, I want existing cards without new fields to continue functioning so that no migration is required and the transition is seamless.

#### Acceptance Criteria

1. THE new card fields (text_stats, classification_result, topics, audience, lifecycle, is_corporate) SHALL be stored in the existing JSONB columns or as nullable top-level fields. No database migration SHALL be required.
2. WHEN the frontend receives a card object without the new fields (e.g., cards created before this redesign), IT SHALL render the card using the legacy layout (original base-analysis display) without errors.
3. WHEN the backend reads an existing card from the database that lacks new fields, IT SHALL populate them with sensible defaults: text_stats=null, classification_result=null (fall back to legacy `classification` field if present), topics=[], audience=null, lifecycle="living", is_corporate=true.
4. THE system SHALL NOT re-analyze existing documents automatically. New analysis only runs on new uploads or explicit user-triggered re-analysis.

**Traceability:**
- Restricción: Backward compatible — cards existentes sin los nuevos campos siguen funcionando.
- Restricción: No requiere migración de DB (JSONB absorbe campos nuevos).
